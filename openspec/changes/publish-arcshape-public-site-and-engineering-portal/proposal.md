# Proposal

## Why

ArcShape has a public architecture reader on GitHub Pages but no public product site, and its generated product model and architecture views do not yet share an engineering entry point. Separate, reproducible static publishing surfaces will make ArcShape understandable to prospective adopters while giving maintainers and readers stable access to current engineering artifacts.

Tracking issue: [#62](https://github.com/juangcarmona/arcshape/issues/62).

## What Changes

- Add a static public product site at `arcshape.dev`, visually in the same family as ProductShape while using ArcShape-owned assets, styles, branding, and current capability claims.
- Add a separate engineering portal at the GitHub Pages root. Publish a Product Snapshot of ArcShape's canonical model and the ArcShape architecture reader under stable routes.
- Keep one GitHub Pages publisher responsible for assembling and deploying the complete engineering site. Preserve the former root reader URL's architecture-section hash links when moving the reader beneath its own route.
- Publish a latest E2E summary only when a completed `main` run produces data that passes the public-summary schema approved with this change and the publisher's run-identity checks. Approval applies to the schema and workflow, not each run. Identify the run, source commit, completion time, and result; keep raw traces and test data private.
- Keep both web surfaces static and independent. Generated views remain derived from their Markdown sources. Do not change the ArcShape product model, add an ArcShape service, or change adopters' hosting choices.

## Capabilities

### New Capabilities

- `public-product-site`: A public, static ArcShape product site at `arcshape.dev`, with reviewable previews and an independent deployment lifecycle.
- `engineering-artifact-portal`: A GitHub Pages entry point that links to reproducible snapshots of ArcShape's product model and architecture, and, when safe output exists, the latest E2E summary.

### Modified Capabilities

None. No existing OpenSpec requirement changes; the current spec inventory contains only `agent-capability-distribution` and `arc42-section-guidance`.

## Impact

- **ArcShape repository:** add public-site source and validation; extend `.github/workflows/pages.yml` and its workflow tests to build the landing page and artifact routes; update the Pages deployment guide and README links. The architecture reader is already generated by `arcshape site build`; ArcShape's existing development-only `@prodshape/cli` tool renders ArcShape's own model to `.product/generated/snapshot.html` for the Product Snapshot.
- **E2E publication:** `.github/workflows/assurance.yml` currently uploads `playwright-report/` and `test-results/` as a 30-day Actions artifact. The design will publish an allowlisted latest summary only from a completed `main` run, while keeping raw traces and ordinary PR artifacts in Actions.
- **External hosting:** Cloudflare Pages serves the product site, using the Git integration pattern recorded in Raccord's ADR-0025. GitHub Actions validates the same build but does not deploy it. GitHub Pages remains the single publisher for engineering artifacts.
- **Product and package boundaries:** ProductShape and ArcShape remain independent products and repositories. ArcShape uses its existing `@prodshape/cli` development dependency only to generate a snapshot of ArcShape's own model; the public sites have no runtime dependency on one another, and this proposal adds no cross-product runtime integration or shared site package. Cloudflare account/domain setup is a deployment prerequisite and must be checked before production activation.

Structural impact was widened from each cited artifact. Neighboring actors, terms, journeys, and use cases were checked, including repository onboarding, architecture authoring and maintenance, ADRs, C4 diagrams, reverse engineering, synchronization, and reading/publishing flows. These remain unchanged because this work adds repository-operated public presentation and does not alter adopter workflows or product behavior. The marketing site itself is project communications, not a new ArcShape-hosted service or product capability; no Product Definition drift or Product Change is required.
